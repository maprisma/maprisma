# Review: 020-disconnect-models

## Round 1 (Antigravity, 2026-11-02, commit 6c77613)

1. **`packages/maprisma_core/lib/src/core.dart:3247-3251, 3906-3920`, `packages/maprisma_core/lib/src/map_edits.dart:529-547` — Action-rule bypass when `_dropRefused` drops a pair on a shared model, when an agent is on two models of the same runner, or when another agent connects before Review**
   - **What goes wrong**:
     1. In `_dropRefused` (`core.dart:3906-3920`), pairs refused by action rules are removed from `action['pairs']`, leaving only the allowed pairs in `left`. However, when the user clicks **Review** (`map.smart_plan`), `_smartPlan` (`core.dart:3247-3251`) strips the agents from `action['pairs']` and passes only the model names (`[for (final p in (action['pairs'] as List).cast<Map>()) '${p['model']}']`) to `edits.modelsDisconnect` (and unlike `mcp_disconnect` at `core.dart:3254-3258`, does not check `params['agents']`). `edits.modelsDisconnect` (`map_edits.dart:529-547`) then looks up **all** `default` edges to `model:runtime:$key:${model.toLowerCase()}` on `currentMap()` and disconnects every agent using that model — including an agent whose pair was dropped by `_dropRefused` because a rule denied disconnecting it.
     2. If a new agent was connected to the model between `map.smart_ask` and `map.smart_plan`, `_enforce(smartCandidateChecks(candidate))` (`core.dart:3218`) only checks the old pairs stored in `candidate['action']['pairs']`, while `modelsDisconnect` disconnects the newly connected agent from `currentMap()` without checking it against the rules.
     3. Because `llm.plan(command, rt, '', false, remove: true)` (`map_edits.dart:546`) removes the entire runner `rt` from `command`, if an agent uses two models on that runner and a rule refuses disconnecting one of them while allowing the other, `_dropRefused` drops the refused pair and keeps the other pair for the same agent — and applying the kept pair disconnects the agent from the refused model too.
   - **How to reproduce**: Connect both `pi` and `codex` to the same model `b.gguf` on `llamacpp`. Add a rule `Deny · Disconnect · Models · b.gguf · Pi` (or `Deny · Disconnect · Models · All · Pi`). In the Models column's Ask AI card, ask to disconnect `b.gguf`. `_dropRefused` filters out `pi` and shows the candidate for `codex`. Click **Review** and **Apply**: `modelsDisconnect` disconnects both `pi` and `codex`, bypassing the deny rule for `Pi`.

2. **`packages/maprisma_core/lib/src/map_edits.dart:549-560`, `packages/maprisma_core/lib/src/plan_worker.dart:132`, `packages/maprisma_core/lib/src/model_guard.dart:412` — Disconnecting 3 or more models of a `can_load` runner fails on Apply with `Invalid model actions`**
   - **What goes wrong**: When `providerFacts['engines'][key]['can_load'] == true` (`ollama`, `llamacpp`, `lmstudio`, `jan`), `modelsDisconnect` (`map_edits.dart:549-560`) adds one `model.unload` action per model in `users.entries` that has users. Both `decodePlan` (`plan_worker.dart:132`) and `validateActions` (`model_guard.dart:412`) reject any plan with `actions.length > 2` by throwing `FormatException('Invalid model actions')` (the old limit from single-model switching, which had at most one unload and one load). Disconnecting 3 or more models in one proposal therefore fails in the worker when **Apply** is clicked.
   - **How to reproduce**: Connect 3 agents to 3 different models on `llamacpp` (or `ollama` / `lmstudio`). In the Models column's Ask AI card, ask *"Disconnect all models of llama.cpp"*, click **Review**, and click **Apply**. `connections.apply` fails with `Invalid model actions`.

3. **`packages/maprisma_core/lib/src/core.dart:3011-3022`, `packages/maprisma_core/lib/src/map_edits.dart:513, 529-536`, `packages/maprisma_core/lib/src/map_graph.dart:489, 557, 649-684` — `used_by` and `modelsDisconnect` miss connected models when `reads.map` has not been scanned yet, when `map_layers` hides models/local/agents, or when a model is past the first 10 on its runner**
   - **What goes wrong**:
     1. `map.smart_ask` (`core.dart:3015`) reads `reads.map['edges']` directly instead of calling `edits.currentMap()` (or building an unfiltered map). Before the first background `map.snapshot` scan finishes (or when automatic map scanning is off and `reads.map` is still empty), `reads.map['edges']` is `[]`, so `used_by` is empty for every model.
     2. `reads.buildMap()` (`read_service.dart:354`, `map_graph.dart:649-684`) filters out nodes and edges hidden by `map_layers`. When the user hides the **Models**, **Local LLMs**, or **Agents** layer on the map, `reads.map['edges']` (and `currentMap()['edges']` in `modelsDisconnect`) contains no `default` edges to local models.
     3. `core.dart:3010-3012` lists `rt.models.take(40)` in `models` and `used_by`, but `map_graph.dart:489, 557` only creates `model:runtime:...` nodes for `rt.models.take(10)` and deletes any edge whose target node is not in `ids`. Models 11–40 therefore never have `default` edges in `reads.map['edges']` or `currentMap()['edges']`, so `used_by` is always `[]` for them and `modelsDisconnect` cannot disconnect them.
   - **How to reproduce**: Uncheck **Models** in the map's layer bar (or connect an agent to the 11th model of a runner with more than 10 models), open Ask AI on the Models column, and ask to disconnect that model. Ask AI replies *"No agent uses it, so there is nothing to disconnect."*

4. **`packages/maprisma_core/lib/src/core.dart:3003-3004`, `packages/maprisma_core/lib/src/smart_card.dart:419, 760-766` — Installed local runners that do not take downloads (`jan`, `vllm`, provider add-ons, or runners without `models_dir`) are omitted from `runtimes`, so Ask AI cannot disconnect their models**
   - **What goes wrong**: `core.dart:3004` includes a runner in `runtimes` only when `rt.installed && _takesDownloads(rt, engines)`. Built-in local runners with `download: ""` (`jan` and `vllm`), local runners from add-ons, and `llamacpp`/`lmstudio`/`koboldcpp` when `rt.modelsDir` is empty are excluded from `runtimes` even when they are installed, have models in `rt.models`, and have agents connected to them on the map. Moreover, `smartProvidersPrompt` (`smart_card.dart:419`) tells the Providers column helper to redirect model-disconnect requests to the `models` column, where those runners are not listed in `runtimes` at all (`smartChecked` rejects their key with `FormatException('no model')`).
   - **How to reproduce**: With Jan or vLLM installed and an agent connected to one of its models on the map, ask in the Providers column *"Disconnect all models of Jan"* and click **Move to Models** (or ask directly in the Models column). Because `jan` is missing from `runtimes`, the Models column cannot propose `model_disconnect` for it.

5. **`packages/maprisma_core/lib/src/map_edits.dart:513, 528-563` — `modelsDisconnect` omits `modelPreview`'s fresh-map, active-provider, and model-on-runner checks, and runs `guard` even when `selected` is empty**
   - **What goes wrong**: Compared to `modelPreview` with `new = null` (`map_edits.dart:400-404, 454, 464-466`), `modelsDisconnect`:
     1. Does not verify `currentMap()`'s users against a fresh `reads.buildMap()` (`map_edits.dart:400-404`) or check `reads.inventory.llm.active(adapter, rt.key)` (`map_edits.dart:464-466`), so within `currentMap()`'s 5-second cache window it can plan against stale edges after an agent's provider/model already changed.
     2. Does not check `rt.models.contains(model)` (`map_edits.dart:454`). On a `can_load: true` runtime, if a model was removed from the runner while `currentMap()` still has its edge, `modelsDisconnect` creates a `model.unload` action for it that then fails in the worker during `connections.apply` (`validateActions` at `model_guard.dart:443`: `FormatException('Model changed')`).
     3. Calls `guard(key, selected)` (`map_edits.dart:550`) before checking whether `selected` is empty. If all agents were already disconnected before **Review** was clicked, `selected` is `[]`, yet `guard` still runs `--guard` against the runtime (which can fail with `'Model is in use; stop its users first'` if the runtime is busy or has `activeAgents`) instead of throwing `'No editable model users'`.
   - **How to reproduce**: Propose disconnecting a model on `llamacpp` in Ask AI, then disconnect the agent on the map while `llamacpp` is generating (or has another active consumer). Click **Review** in Ask AI after 5 seconds: `guard(key, [])` fails with `'Model is in use; stop its users first'` even though no agent uses the model in the plan.

6. **`flutter_app/lib/main.dart:4606-4644` (vs `3561-3595`) — Applying `model_disconnect` in Ask AI does not sync model slots (`_syncSlots`) or show the `context_failures` warning**
   - **What goes wrong**: When a model is disconnected on the map via `_connectionPreview` (`main.dart:3561-3595`), the app shows the `'Configuration saved; some model operations could not be completed.'` snackbar if `(result['context_failures'] as num? ?? 0) > 0` and then calls `await _syncSlots()` (`models.slots_preview`) so local LLMs update how many models they keep loaded at once. When `model_disconnect` is applied in Ask AI (`_applyConnect` in `map_smart_card.dart:1022-1047` → `onSmartApplied` in `main.dart:4606-4644`), `onSmartApplied` neither checks `result['context_failures']` nor calls `_syncSlots()`.
   - **How to reproduce**: Connect two agents to two models on `llamacpp` (with 2 slots configured), then disconnect one or both models via Ask AI in the Models column and click **Apply**. The disconnect completes without calling `models.slots_preview` to sync the runner's slots (and silently drops any `context_failures` from `model.unload`).

### Answers (Claude)
1. Fixed. The pairs decide who leaves. A card holds all an agent's models on that LLM, one refused model keeps that agent, and `modelsDisconnect` refuses when the pairs no longer fit the fresh users. A model unloads only when nobody stays on it.
2. Fixed: `maxModelActions` in both checks. Tested through `decodePlan`.
3. Fixed: `ReadService.modelUsers` builds with no layer hidden and no limit of ten, fresh.
4. Fixed: `model_users` lists every installed local LLM with models; the download list stays as it is.
5. Fixed: `_canLeave` is shared; the fresh users and the empty check come first, and `guard` runs only with agents.
6. Fixed: `_modelsLeft` after Apply, as after a drawn line.
