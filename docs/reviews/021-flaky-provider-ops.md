# Review: 021-flaky-provider-ops

## Round 1 (Antigravity, 2026-11-02, commit 2d4da6a)

1. **High** `packages/maprisma_core/lib/src/provider_scans.dart:284` When `llama-server` runs in router mode and spawns a child `llama-server` process for a loaded model on its own internal port (`--port <child>` and `-m <model>`), `ProviderScans.scan()` does not skip child `llama-server` processes whose parent PID is another `llama-server` (unlike `inventory.py:238-244` and `packages/maprisma_core/lib/src/model_slots.dart:267-278`). Because the child process has a higher PID than the router, `ProviderScans.scan()` visits the child after the router and overwrites `rt.address` with the child's internal port. Reproduce: run `llama-server` in router mode on port 8080 and load a model so it spawns a child `llama-server` with `--port <internal>`; `ProviderScans.scan()` reports `rt.address` as `127.0.0.1:<internal>` instead of `127.0.0.1:8080`, breaking `model.load`, `model.unload`, `loadedModels`, and parity with Python in `tests/test_dart_provider_ops_parity.py`.
2. **Medium** `tests/test_dart_provider_ops_parity.py:71` Both workers in `tests/test_dart_provider_ops_parity.py` still scan the PC's real `/proc` (`inventory.own_processes()` at `inventory.py:216-228` and `ProviderScans.processes()` at `packages/maprisma_core/lib/src/provider_scans.dart:59-77`). Because `inventory.llamacpp`, `inventory.ollama`, and `ProviderScans.scan` iterate `/proc` in PID order and overwrite `rt.address`, `folder`, and `env` with each matching `llama-server` or `ollama serve` process: (a) a real `llama-server` on the PC with `LLAMA_ARG_MODELS_DIR` in `/proc/<pid>/environ` or `--models-dir` in `cmdline` leaks its model folder into the test's `rt.models_dir` (since the test's fake `llama-server` only passes `--port`), and (b) any real `llama-server` or `ollama serve` started after the test's fake server (or with a higher PID after PID wrap-around) overwrites `rt.address` with the real server's port. Reproduce: start a `llama-server --port 8080` or `ollama serve` on the PC after the test's `seed()` starts its fake server (or have a higher-PID `llama-server` in `/proc`) while running `tests/test_dart_provider_ops_parity.py`.
3. **Low** `gpu_usage.py:90` `GPU_DIR`, `HWMON`, and `GPU_SLOT` are evaluated once at module import time (`GPU_DIR = discrete_gpu()`), and `gpu_totals()` (`gpu_usage.py:109-113`) checks `if GPU_DIR:` before `if os.environ.get("MAPRISMA_SCAN_GPU"):`. This works in `flutter_worker.py` only because it is a fresh subprocess with `MAPRISMA_SCAN_GPU` already in `os.environ` before `gpu_usage` is imported; if `MAPRISMA_SCAN_GPU` is set after `gpu_usage` is imported (or set to `""`, where Python's `os.environ.get("MAPRISMA_SCAN_GPU") or "/sys/class/drm"` falls back to `/sys/class/drm` while Dart's `_drm ?? '/sys/class/drm'` does not), Python still reads the PC's real `/sys/class/drm` and `nvidia-smi`. Reproduce: import `gpu_usage`, then set `os.environ["MAPRISMA_SCAN_GPU"] = "/nonexistent"` and call `gpu_usage.gpu_totals()` or `gpu_usage.gpu_busy_percent()`.

### Answers (Claude)
1. Fixed: the Dart scan skips a llama-server whose parent is one, as `inventory.llamacpp` does. Test: `router_children_test.dart`. This was a fault of the app, not only of the test.
2. Fixed: the test gives both workers a /proc with only its fake server, through `MAPRISMA_SCAN_PROC`, which `inventory.own_processes` now reads too.
3. Fixed: `gpu_totals` reads `MAPRISMA_SCAN_GPU` on each call, and an empty value means no cards in both cores.
