1. **High** [ai_project_center.dart:3401](packages/maprisma_core/lib/src/features/ai_project_center.dart#L3392-L3427) (`_scheduledRun` at lines 3401 and 3425): `_removeTimer(id)` is fired with `unawaited(...)` instead of awaited inside `_serial`. Because `_scheduledRun` returns `'no_schedule'` / `'ended'` immediately, `_serial` completes and drops `_scheduleBusy` back to `0` while `scheduler.remove(id)` is still running `systemctl disable --now` / deleting files.
   - **Race with `set_schedule`:** While `remove(id)` is suspended on `systemctl`, a user calling `set_schedule` for the same project enters `_serial` immediately and runs `scheduler.install(id, ...)` concurrently with `remove(id)`; the older `remove(id)` can disable or delete the newly installed unit files.
   - **Premature headless shutdown:** In [project_schedule_run.dart:98-114](packages/maprisma_core/lib/src/features/project_schedule_run.dart#L98-L114), `serveScheduledRuns` treats `plugin.idle` (`_active.isEmpty && !_taking && _scheduleBusy == 0` at line 3384) as idle immediately. If `systemctl` takes longer than two quiet polls (4 s, while `_run` allows up to 60 s), `serveScheduledRuns` calls `plugin.shutdown()` (setting `_closed = true`) and exits mid-removal, preventing `_timerTrouble` from recording `schedule_timer_failed` (guarded by `!_closed` at line 3307) or notifying.
   - **Repeated `ended` events defeating dedup:** When an `until` schedule has ended and its timer cannot be removed, each subsequent trigger after `until` has a newer `slot`, writes another `schedule_ended` event ("its timer was removed") as `events.last`, and then `_removeTimer` fails again; because `events.last['type']` is now `'schedule_ended'` instead of `'schedule_timer_failed'`, the dedup check at lines 3312–3314 is bypassed on every firing.
   - **Suggested fix:** Make `_scheduledRun` return `Future<String>` and `await _removeTimer(id)` at lines 3401 and 3425 so removal stays serialized in `_serial` and keeps `plugin.idle == false` until complete. In the `ended` branch, avoid re-appending `schedule_ended` on later firings when `schedule_ended` was already recorded (or clear `schedule` / check whether removal succeeded before claiming "its timer was removed").

   > Author: confirmed (both `unawaited(_removeTimer(id))` in `_scheduledRun`). Fixed in fb524392: `_scheduledRun` is async and awaits the removal inside `_serial`, so set_schedule waits and `idle` stays false; the `ended` event is recorded once (a later slot that is also past the end only retries the removal). Tests: "a removal is awaited in the chain…", "the headless owner is not idle while a timer is removed", "an ended schedule is recorded once…" (all fail on ea9807e0).

4. **Medium** [flutter_app/lib/ai_project_center.dart:2278-2292](flutter_app/lib/ai_project_center.dart#L2278-L2292), [desktop_schedules.dart:227-228](packages/maprisma_core/lib/src/desktop_schedules.dart#L227-L228), [desktop_schedules.dart:301-303](packages/maprisma_core/lib/src/desktop_schedules.dart#L301-L303), and [ai_project_center.dart:3279-3316](packages/maprisma_core/lib/src/features/ai_project_center.dart#L3279-L3316): Multi-line `systemctl` stderr, control characters, and unbounded non-`ServiceError` reasons break Flutter's `_eventText` translation regex, event deduplication, and potentially store reload.
