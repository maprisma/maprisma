# Ask AI without categories

## What the user should experience

Open **Ask AI** from the map and type or dictate “Which model will run on this PC and work with my agent?” One press of **Ask** should be enough. Maprisma can check the available memory, installed models and agent connections, explain a recommendation, and offer **Review connection** if there is a compatible choice. If two agents are plausible, it can ask “Which agent do you want to use?” with their names and a field for another answer. The user should never have to decide whether their question belongs to Agents, Providers, Models or MCP.

Keep the four map columns for people exploring their setup. Keep category filters in the health overview, where they help people inspect findings. Remove the chips, category-prefixed placeholder, category heading and “Move to …” step from the main question journey. The map and health detail can supply context when a person opens Ask AI on a particular item. Opening Ask AI or answering a question should preserve the person's saved map layers.

## Example interactions

| The user asks | What Maprisma should do |
| --- | --- |
| “Why is the AI on my computer slow?” | Use the current runtime and hardware facts. If measurements are missing, offer Open Performance and say what it can check. |
| “Let my agent search the web.” | Check which installed agents and tools can do that. Offer the existing connection or setup review, naming the affected agent and tool. |
| “Can I run this offline?” from a model on the map | Use that model as context. From the general Ask AI button, ask which model or task the person means if the answer depends on it. |

## Findings from Antigravity's independent review

- **Give diagnostic questions the facts they need.** “Which agents need sign-in?” and “Which agents have updates?” are built-in examples. The agent facts include whether the app can *offer* login or update. Those flags cannot establish that a particular agent needs either one. MCP inventory similarly omits the cached update findings. Use the same observed sign-in and update evidence as the map, with an explicit unknown or last-checked state. Test two installed agents with the same capabilities and different status, plus a stale MCP update check. Where Maprisma already knows the answer, display it directly from the core without spending helper tokens. [Agent facts](../packages/maprisma_core/lib/src/core.dart#L3310) · [MCP facts](../packages/maprisma_core/lib/src/core.dart#L3610)
- **Protect saved suggestions before changing their layout.** If the card first mounts before the core client is ready, it skips loading suggestions. A subsequent save can replace suggestions from all categories with a partial set. Load when the client becomes ready, guard edits during loading, and merge with current settings on save. Test a cold start with custom Agents and Models suggestions, then edit one and reopen. Both groups must survive. [Suggestion loading and saving](../flutter_app/lib/map_smart_card.dart#L1840)
- **Show dictation status before recording.** On first open the widget assumes dictation is enabled and unconfigured until it fetches the snapshot. An online setup can start recording on the same click that first discovers its cost. Check off, ready-local and ready-online states before enabling the mic. Verify the user can see the online cost before recording. [Dictation start](../flutter_app/lib/map_smart_card.dart#L1661)
- **Make Back and Cancel return to the step the user came from.** Back from a review can discard a proposal. Cancelling an MCP connection preview can force the user to re-enter form values. Return to the populated form or previous proposal and retry only the failed operation. Keep sensitive form fields in memory only while the form is needed. Test returning from review and changing a selection without contacting the helper again. [Back handling](../flutter_app/lib/map_smart_card.dart#L917) · [MCP form](../flutter_app/lib/map_smart_card.dart#L1106)
- **Show when Apply is working.** While applying a connection, the button can still look available and a second click appears to do nothing. Disable duplicate submissions, show progress, and preserve a safe, localized cause when a helper becomes unavailable, a model is missing or a proposal expires. Verify one apply call on a slow double-click. [Connection apply](../flutter_app/lib/map_smart_card.dart#L1405)

## Recommended delivery order

### 1. Make one question work across the map

Start with the diagnostic facts and saved-suggestion protections above so the simpler entry gives correct answers and preserves existing work. Give Ask AI a visible text label at normal desktop widths and an accessible compact button at narrow widths. Focus a single field, “What would you like to do with your AI setup?” Keep a few editable examples phrased as goals, such as “Why is my local AI slow?”, “Which model fits this PC?” and “Let my agent search the web.” Choosing an example fills the field. The user sends it. Bring existing saved suggestions together in **My suggestions**, preserving customized text, built-in IDs, ordering within each old group, and the ability to edit and remove them.

**Core design.** Add an explicit automatic mode to the Dart contract, for example `map.smart_ask(column: "auto", …)`. Preserve the four explicit values and their existing result shapes for callers that use them. Use the first helper decision to identify an answer, clarification or supported operation across all four areas. Give it a small catalog of available operations and the minimum relevant map facts. Deterministic hints from a selected finding, saved preset or recognized legacy prefix can narrow the choices. Ordinary language in all eight languages must work without a prefix. Avoid a separate paid classification call and avoid parallel requests to all four handlers.

Extend the core to pass the first decision into the matching existing validator and collector. Fetch detailed PC, catalog or connection facts only where the question needs them. For a mixed request, use facts from multiple areas in one answer. For a request such as “find a model and connect it”, show availability and fit first, review a download if needed, then offer the existing checked connection once it is available. Recheck current state and rules at each step. A missing permission, model, or second step must leave the first step's actual outcome clear. Never let a helper create an executable action or choose a route outside the core's allowlist.

**Release check.** Send a plain question from each of the four areas and two cross-area questions with Agents initially selected and the Models layer hidden. All six reach a useful answer, clarification, or correct manual preview after one submission and zero category selections. No hidden layer becomes visible on reopening the map. A genuinely ambiguous request asks about the user's goal or the relevant item. Opening the page, selecting an example or handling an internal redirect starts no extra helper call.

### 2. Make asking and stopping dependable

Fix early cancellation independently of automatic routing so it can ship first. Keep track of the pending start. If a cancelled request later receives an ID, cancel that specific job once even if a new question has started. Treat a confirmed download or apply according to its existing background-job rules. Show a real job stage when the service knows it, such as checking the setup or searching a catalog. Avoid guessed percentages. Disable Ask for blank input, show the same length limit as the core before sending, retain the draft on failure, and distinguish **Edit question**, **Retry** and **Set up helper**. Retry should send only after its own click.

Keep the field and examples usable with no helper. Distinguish loading, unavailable and ready, offer a direct setup path and refresh the available helpers on return. Show the effective helper and **Local** or **Online · uses plan/tokens** beside Ask. If an explicitly chosen helper vanishes, ask the user to choose a replacement before sending. Keep the existing Ask AI and Reports helper choice for this release. A later family-wide preference migration needs a decision on local model IDs, existing selections and unavailable helpers. Use the family's shared microphone control, already used by Reports, with draft-preserving dictation and an accessible send button.

**Release check.** Exercise Cancel and Esc before and after the task ID appears, delayed replies after a second question, a timed-out helper, unavailable local helper with an online alternative, empty input, and lengths of 2,000 and 2,001. Confirm the call counts, retained draft and effective destination. Confirm a preview alone writes nothing and an already confirmed job can still be found from the map.

### 3. Make answers readable and easy to follow up

Add a distinct answer result for the automatic mode. Lead with one direct answer, then show the specific evidence behind it, such as installed model size, available memory or the agent's active connection. Separate observations from estimates and clickable HTTPS sources from the answer text. Label a proposed next step with its effect, such as **Review download** or **Open Performance**. Reuse the existing manual preview, Apply, rule recheck and Undo where supported.

Offer a follow-up field under the answer and a separate **New question** action. Allow typed clarification alongside suggested replies. Start with a bounded, in-memory reference to the previous question, checked result and selected item. Expire it on a new question or session end, re-read mutable facts, and explain if a proposal has expired. Keep raw prompts out of Reports and persistent history. Switching a follow-up from local to online requires an explicit choice about sending its previous context.

**Release check.** “Why that one?” can refer to the model just recommended. A follow-up after the model is removed uses current facts. Clarification still works with zero suggested answers. Explain-only requests complete without opening a review. A denied or expired proposal gives the person an actionable explanation and cannot be applied.

## How to judge success

1. Use repeatable fixtures for an empty installation, local-only setup, online helper, two agents with similar names, insufficient disk space, a denied change and unavailable network. Include plain-language formulations in all eight UI languages. For each request record the expected answer or action, the grounding facts, the user decisions and the permitted helper calls. Use fake helpers for regression tests. Keep intentional, consented live-helper evaluations separate and record their failures as well as their successes.
2. Compare today's UI with the new flow on the same goals. Ask first-time users to find a fitting model, explain a failed connection and connect a tool without coaching. Observe whether they can start unaided, identify what will change, and decline or cancel. Count resubmissions and time to the first useful answer. Treat any unwanted change, silent online fallback or compulsory category selection as a release blocker. Measure helper calls and latency on the same fixtures before setting performance targets.
3. Check keyboard-only use, screen-reader names and focus, text scaling, long translations, the smallest supported overlay, and light/dark screenshots. Keep Enter to ask, Ctrl+Enter for a new line, Esc to the map and Back within the flow. Update the eight manuals, including passages that still describe per-column Ask AI bars. Ship any wire change in protocol → core → GUI order with the relevant checks and independent review. [Current manual](manual/manual.html#dictation-flutter) · [Current protocol](protocol.md)
